# meeting-calendar-monitor · 俄乌 / 美伊关键人物会晤日程

每天抓取公开信源，把「谁和谁、什么时候、在哪、见没见成」整理成一张**会晤日程表**。
输出 `output/LATEST.md`（人读）与 `output/LATEST.csv`（机读）。

它回答的是**日程**，不是新闻流，也不是立场分析：

| 日期 | 会议 / 地点 | 关键人物 | 确认情况 | 依据 |
|---|---|---|---|---|
| 2026-10-27 | 第八届 GECF 领导人峰会，莫斯科 | 佩泽希齐扬、普京 | 已确认 | 基线 |
| 2026-10-27 | 俄伊领导人双边会晤，莫斯科 | 佩泽希齐扬、普京、阿拉格齐 | 已安排 | T2 IRNA +23 |
| 2026-11（月内） | 美伊潜在新一轮谈判，地点未定 | 威特科夫、库什纳、阿拉格齐 | 暂无确认日期 | 基线 |

## 1. 怎么跑

```bat
run.bat
```

`run.bat` 会把参数**透传给抓取步骤**，所以下面这些都能直接写在 bat 后面：

```bat
run.bat --proxy http://127.0.0.1:7897   :: 指定出口
run.bat --proxy direct                  :: 强制直连（排障用）
run.bat --verbose                       :: 打印每源条数
```

双击跑完会自动打开 `output/LATEST.md`；不想弹窗就先 `set RM_OPEN=0`。
退出码：`0` 成功 / `1` 自检失败 / `2` 抓取失败 / `3` 对账失败。

三步流水线（`run.bat` 只负责找解释器，逻辑都在 `meeting_monitor.py`）：

```bash
python meeting_monitor.py --selftest      # 1 离线自检，不联网
python meeting_monitor.py                 # 2 抓取 + 抽取 + 归并 + 渲染
python tools/verify_report.py --save      # 3 独立复算报告与 CSV
```

调试出口：

```bash
python meeting_monitor.py --proxy http://127.0.0.1:7897   # 指定出口
python meeting_monitor.py --proxy direct                  # 强制直连
python meeting_monitor.py --verbose                        # 打印每源条数
python meeting_monitor.py --today 2026-10-30               # 覆盖运行日（测试生命周期）
```

定时任务请设 `RM_NO_PAUSE=1`（否则结尾会等回车）。

**建议每天北京时间 08:30 之后跑一次。** 早于此，欧美前一日的稿件尚未完全入库。

## 2. 产出与落盘

```
output/
  LATEST.md / LATEST.csv / LATEST.jsonl      # 最新一次（人读 / 机读 / 全字段）
  YYYY-MM-DD/
    meetings-YYYY-MM-DD.md                   # 当日快照
    calendar.csv
    signals.jsonl                            # 被采纳的信号（含原文引证片段）
    rejects.jsonl                            # 被拒的条目 + 拒收原因（审计用）
    raw/<source>.xml                         # 原始载荷，仅 HTTP 200 才留
    _source_health.json                      # 每源条数、最新条目、失败原因
    _stats.json
  _verify_last.json                          # 最近一次对账结果
state/
  events.json                                # 累积事件表（含全部 claim 与状态变更）
  transitions.jsonl                          # 状态变更台账（只增不改）
```

`state/events.json` 是主数据。**历史只增不减**：同一事件被反复报道会不断并入
同一条（`EV-0001` 这类 ID 永不重算），状态变更写入台账。

### 2.1 每个文件给谁看

| 文件 | 读者 | 里面是什么 | 何时重写 |
|---|---|---|---|
| `LATEST.md` | 人 | 10 节报告：速览 / 主表 / 分轨 / 人物索引 / 状态变化 / 过期未证实 / 已举行 / 源状态 / 基线核验 / 口径边界 | 每次运行 |
| `LATEST.csv` | Excel | 19 列，UTF-8 **带 BOM**（双击不乱码），一行一会晤 | 每次运行 |
| `LATEST.jsonl` | 程序 | 全字段：`claims` / `sources` / `updates` 全留 | 每次运行 |
| `_verify_last.json` | 巡检 | 对账 18 项结果 + `failed` 明细 | 每次运行 |
| `YYYY-MM-DD/meetings-*.md`、`calendar.csv` | 归档 | 当日报告的**不可变快照**（后续改口径也不会回头改它） | 每次运行 |
| `YYYY-MM-DD/signals.jsonl` | 审计 | 被采纳的信号 + 引证片段，**按 (标题,链接) 跨运行合并去重** | 累加合并 |
| `YYYY-MM-DD/rejects.jsonl` | 审计 | 每条被拒的稿 + `reason`，用来回答「为什么这条没进表」 | 累加合并 |
| `YYYY-MM-DD/raw/*.xml` | 复算 | 原始载荷，**仅 HTTP 200 才落盘**；换解析规则可原地重算 | 每次运行 |
| `YYYY-MM-DD/_source_health.json` | 排障 | 每源条数 / 最新条目 / 失败原因（`HTTP 403` 之类） | 每次运行 |
| `YYYY-MM-DD/_stats.json` | 排障 | 本轮计数 + 拒收原因分布 + 当日快照唯一条数 | 每次运行 |
| `state/events.json` | 主数据 | 累积事件表，含全部 claim 与状态 | 每次运行 |
| `state/transitions.jsonl` | 台账 | 状态变更流水（只增不改，用于解释「为什么今天升级了」） | 有变化时追加 |

> **别把行数当条数**：`signals.jsonl` / `rejects.jsonl` 是当天历次运行合并的结果
> （同一天补跑、定时+手动各一次都会写）。早期版本用 `append`，实测同日 3 次运行后
> 754 行只对应 148 条不同稿件——文件看起来很健康，读数却虚高 5 倍。
> 现在按 `(标题, 链接)` 合并去重，`_stats.json` 里的 `signals_daily_unique` /
> `rejects_daily_unique` 才是当日真实条数。

## 3. 口径（这部分比代码重要）

### 3.1 确认度是分级，不是布尔值

```
已确认 > 日期已定 > 已安排 > 已预告 > 媒体报道 > 暂无确认日期
已否认 / 已推迟 / 已取消 / 过期未证实   —— 单列，不参与排序
```

- **强信源否认压过弱信源宣布**：T2 及以上的 `denied` 会把事件翻成「已否认」。
- **弱信源不能抬升**：一条 T3 的「据报道」不会把事件变成「已确认」。
- 强信源与弱信源**同时存在且互斥**时，标 `⚠口径冲突`，两边原文都留在 `claims` 里，不替你裁决。
- **情态降级**：`Kremlin confirms ... could hold a three-way meeting` 里的 confirms
  确认的是「有可能」，不是「已确认」。含 `could / may / might / open to` 的标题一律降为「已预告」。

### 3.2 「过期未证实」是一等状态

到了日期、又没有任何一方确认举行 → `lapsed`。**不删除，也不假装它发生过。**

理由：会晤「没开成」和「开了但没人报道」在公开源上长得一模一样。
静默删除等于替读者做了一个无法验证的判断。

### 3.3 日期精度

`日 / 区间 / 当周 / 月内 / 待定`。

- 「月内」来自原文 `in November` / `next month`，**不是我们推断出的具体某天**。
- 月份精度的条目在表内**按该月月初排序**（对外只承诺月份，排序就用月份）。
- 解析不出日期时返回 `None` 并记账，绝不猜。`--today` 只影响生命周期判定。

### 3.4 基线（anchors）

已知的固定峰会（G20、APEC、GECF、美国中期选举…）写在 `config.json → anchors`，
带 `verify_query` 与 `match_any`。规则：

- 基线进入时标 `baseline=true`，报告 §9 单列「是否被公开源证实」。
- **只有 `snap: true` 的基线参与吸附**——即「会期是日历常数」的命名峰会。
  双边会晤的日期是事件属性，不能吸附（否则一条「10-27 莫斯科」会成为磁铁，
  把所有双边消息吸过去，实测一次吸错 97 条）。
- 基线对**峰会本身**的状态有权威：APEC 的「已定档」不会被某家媒体的
  「could meet at APEC」降级。

### 3.5 信源等级

| 级别 | 含义 | 本项目的源 |
|---|---|---|
| T1 | 官方一手 | 白宫、美国国务院、克里姆林宫 |
| T2 | 主流媒体 / 官方背景通讯社 | TASS、IRNA、Mehr、Ukrinform、Al Jazeera、Times of Israel、Tehran Times |
| T3 | 聚合检索（只作线索） | Google News 按人物/议题检索 |
| B | 人工基线 | `config.json → anchors` |

**T3 只用于发现，不用于定论。** 每条记录保留原始链接，可逐条回溯。

## 4. 抽取是怎么做的

1. **标题优先，正文只做补全。** 一篇 3000 字新闻稿里任意一句 `met with ...`
   都不该决定这条新闻的性质。正文只在「像摘要」（≤220 字符）时才提供地点。
2. **人物**：别名词典 + 词边界。`Trump` 不会命中 `Trumpism`；`Katz` / `Saa'r`
   这类易混姓氏需要职务上下文（`Defense Minister Katz`）才认。
3. **地点**：城市/场馆词典，并排除媒体名（`Tehran Times` 不是德黑兰、
   `Washington Post` 不是华盛顿）。
4. **日期**：显式日期（含区间、`Nov. 18-19`、`18-19 November`）、相对日期
   （`next week` / `next month` / `tomorrow`）、月份精度；含跨年推断与合法性校验
   （`November 31` 直接判失败，不猜）。
5. **否定守卫**：`She has not met with ...` 不会命中「已举行」。
6. **人物门槛**：只有 1 个名字、无法确定对谈方的条目一律拒收（`single_person`）。
7. **归并**：按「事件类型 + 人物集合 + 日期接近 + 地点不冲突」合并。
   月份精度只允许**子集合并**（双边报道并入三方峰会）；待定事件要求人物高度重合，
   防止 `tbd` 变成万能胶水。
8. **拒收也留档**：`rejects.jsonl` 记录原因，报告 §10 汇总计数。

## 5. 怎么扩展

**加人物**：在 `config.json → persons` 增加一条，填 `zh / role / country / aliases`。
容易混淆的姓氏放进 `weak`，需要职务上下文才会命中。

**加检索**：在 `config.json → queries` 加一条 Google News 查询，标好 `track`。

**加直连源**：在 `sources` 加 RSS；若站点没有 RSS，`kind: "html"` 并补一个解析函数。

**加基线**：在 `anchors` 加一条，必须给 `verify_query`；只有确定「会期是日历常数」
的才设 `snap: true`。

**改确认度词典**：`status_lexicon`。注意**先判更弱、更具体的那一档**
（`plans to` 必须先于泛化的 `to meet`），否则会被抬成「已安排」。

改完务必跑 `--selftest`，并重跑一轮真实抓取看 `rejects.jsonl` 的原因分布有没有异常。

## 6. 已知偏差（读报告前请先看）

- **人物识别是词典不是 NER**：非常规称呼若没进别名表就会漏；代词不识别。
- **一条新闻可能支撑两个会晤**，当前只取最强的一个日期，可能漏掉第二个。
- **地点只认城市表**：「在峰会间隙」这类没有城市的表述会落成「地点未定」。
- **聚合检索会重复转载**：已按标题+日期去重，但措辞差异大的同一事件仍可能分两行。
- **失败源 = 覆盖缺口**：某源 403/超时不会中断整轮，但该源覆盖的会晤可能整段缺失。
  报告 §8 会逐源列出状态与最新条目日期。
- 本表服务于**日程跟踪**，不构成对会晤能否举行、或冲突走向的判断。

## 附录 A · 建这个项目时踩过的坑（都是真数据暴露的）

**A.1 gzip 假成功。** `urllib` 不会自动解压，而 curl 会。于是探测脚本一切正常，
爬虫却拿到 HTTP 200 + 正常字节数 + 解析 0 条，报告显示「✅ 0 条」，像个空源。
→ `_decompress()` 按魔数解压；并加护栏：**200 + 有字节 + 0 条 = 失败**，不许显示成空源。

**A.2 长正文的证据错位。** 国务院新闻稿里一句 `The spokesman met with reporters`
把整条（标题是「愿意举行三方会谈」）打成「已举行」，顺带把地点定到华盛顿。
→ 标题优先；「已举行」只允许来自标题；正文地点仅在 ≤220 字符时采信。

**A.3 基线磁铁。** 给所有基线都开了吸附，结果「双边会晤 10-27 莫斯科」成了磁铁，
97 条互不相干的信号（赫格塞思见内塔尼亚胡、鲁比奥见泽连斯基…）全被吸过去。
→ 只有 `snap: true` 的命名峰会才吸附。

**A.4 月份精度磁铁。** 所有「11 月」的事件都被吸到 `11-01`，一场会晤能吞掉四五个议题。
→ 月份精度只允许子集合并；显示与排序统一按月初。

**A.5 人名并集 ≠ 同桌的人。** `Putin floats summit with Trump and Xi ... without Zelensky`
会让泽连斯基进入并集，标题渲染成「四方会晤」。→ 标题只用核心 2–3 人；
展示人物按报道频次取前 3–4；事件身份用「包含度」判重而不是全并集。

**A.6 对账工具的假告警。** 用 `cell[:10]` 截「2026-11（月内）」，切进全角括号，
字符串比较立刻乱序，报告明明是对的却报错。→ 用正则取 `YYYY-MM(-DD)` 再补全。
**对账工具出错和报告出错一样危险**：它会训练你忽略告警。
