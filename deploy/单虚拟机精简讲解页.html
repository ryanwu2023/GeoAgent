只保留一台虚拟机

按本次确认，取消独立备份机器、应急机器、4TB 备份盘和应急 SSD。本版只申请一台 VM，集中部署 GitLab、镜像仓库、Runner、GeoAgent、业务 PostgreSQL 和入口代理。原多节点方案保留供参考，当前精简方案以本版为准。

32GB 内存逐项分配

下表的“预算”是部署时为各类负载留出的容量，不是实测常驻占用，也不是写进文档就已生效的容器上限。“轻载估计”仅用于解释规模，最终以锁定版本、真实数据和并发压测为准。GB 按本方案内存标称口径计算，实际容器参数须统一单位。

组件 轻载／运行时大致占用（估计） 内存预算 包含什么、如何限制
GitLab 服务整体 约 5–8GB 8GB 包含 Web、后台作业、Gitaly、GitLab 自带 PostgreSQL 和 Redis；这些内部服务不再重复计费。按小团队低并发调优
内网镜像仓库 Registry 约 0.2–0.5GB 1GB 镜像接收和下载；镜像文件主要占磁盘。若在 GitLab 安装包内运行，GitLab＋Registry 整体按 9GB 管理
GitLab Runner 管理进程 约 0.1–0.3GB 0.5GB 接任务、启动作业和上传日志；不包含构建容器内存
构建／临时测试共享池 空闲约 0GB；活动约 2–4GB 4GB 包含构建器、辅助容器、测试应用及测试 PostgreSQL。构建与集成测试分阶段串行，共用同一额度，不各算 4GB

GeoAgent 业务 PostgreSQL 约 1–3GB，随查询变化 4GB 业务库，独立于 GitLab 自带数据库；包含连接、缓冲、查询与后台维护空间
采集／翻译／MCP 同步任务 空闲接近 0GB；活动约 0.5–2GB 2GB 单队列限制重任务并发；不同时全量采集、翻译和导入多个大快照
Nginx／入口代理 约 0.05–0.2GB 0.5GB 域名入口、TLS、认证转发；如有其他业务代理也计入此项
操作系统、Docker、基础日志 约 2–3GB 3GB 系统和运行时基本开销；轻量日志轮转，不在此预算内额外部署重型监控套件

合计 实际会随负载变化 32GB 服务、任务、系统预算 27GB ＋余量 5GB

GitLab 的 8GB 是有条件的

GitLab 官方当前单节点基线为 16GB，也说明受限环境可在至少 8GB 下运行。因此这里采用 8GB 是小团队的节省资源配置，需按锁定版本减少不必要组件、调整并发并压测，不能承诺默认安装任何版本都够。升级前复测；实测持续超预算时，应调优、拆出构建负载或扩容整机，不能随意挤占生产数据库和预留空间。GitLab 官方安装要求

PostgreSQL 的 4GB 不是全部配置为缓存

业务库可以从 shared_buffers=1GB、work_mem=4MB、maintenance_work_mem=128MB、max_connections=40 开始验证；这些是待压测参数，不是已生效配置。查询工作内存可能按多个查询节点、连接及并行进程重复分配，必须控制并发。不要把共享主机的 32GB 当作数据库专属内存来设置缓存。PostgreSQL 17 内存参数

同一份内存不能重复计算

  • Runner 本身只安排任务，真正吃内存的是构建器和测试容器，因此两项分开列。
  • 构建容器停止后再启动集成测试应用和测试库；两阶段共用 4GB。测试库不使用正式 PostgreSQL 的账号或业务数据库。
  • GeoAgent 在线功能合计 4GB；若后台任务仍嵌入在线进程，就要调整进程拆分和整组限额，不能宣称同一个容器同时拥有两份独立保障。
  • Linux 页缓存可能计入容器 cgroup。实际核算结合容器统计、宿主可用内存和 OOM 事件，避免把共享内存或缓存重复相加。

一台机器里面怎样连接

研发通过客户 VPN／跳板机访问 GitLab。Runner 拉取代码，在同机启动短时构建／测试容器，测试通过后由受保护发布作业更新应用。客户用户经业务域名和 Nginx 访问 GeoAgent，再由 GeoAgent 连接业务 PostgreSQL。

GitLab 自带 PostgreSQL 和 Redis 为代码平台服务；GeoAgent 的业务 PostgreSQL 单独容器、账号与数据目录。它们在同一台机器，但不能混成同一个业务数据库。

服务器集中后，应用、数据库和发布工具会受到同一台宿主故障的影响。此方案没有另一台机器可以接管。

04 / 发布与测试

发布与测试如何避免抢业务资源

  1. 研发通过 VPN／跳板向客户 GitLab 推送代码，凭据与生产配置不进入普通仓库。
  2. Runner 全局最多运行一个资源密集作业，构建池控制在 2 vCPU／4GB 内；构建器和所有辅助容器合计计算。业务 CPU 共享剩余能力，具体调度以压测为准。
  3. 构建完成后退出构建进程，再运行临时测试应用和测试 PostgreSQL，共用 4GB；不能同时开两份完整环境。
  4. 测试与正式的账号、库、目录、端口、外部写入目标分别配置；临时测试使用脱敏副本或测试数据。
  5. 通过后发布同一已验证镜像 digest。发布前保留上一稳定镜像、配置和数据恢复点，在维护窗口执行迁移与重启。
  6. 验证登录、页面、数据库读写、MCP 接口；通过才开放正常访问。数据库回退不能仅靠切换旧镜像。
  7. 回收测试容器、临时数据库和构建缓存；配置保留规则，数据盘保留约 30% 空闲容量。

白天优先用户访问；构建、全量同步、翻译、压缩导出尽量错峰。按 5 和 10 并发验证页面和重操作，再验证叠加单个后台任务或单个构建作业时的情况。如果出现 OOM、交换空间持续读写或业务延迟超出验收目标，先停止可延迟任务，再调整配置。

本版没有常驻独立测试环境，也不提供双版本灰度或无停机发布。临时测试的逻辑隔离不能代替物理故障隔离。

05 / 故障怎么处理

取消备份机器后，数据与故障怎样处理

当前配置清单只包含 VM01，不新增任何备份服务器、备用 VM 或专用备份盘，也没有承诺客户已有备份资源已经配置好。

如果客户已有 NAS、对象存储或虚拟化备份服务，可把数据库、GitLab 仓库/密钥、Registry 和业务文件备份接入现有存储，不需要新增备份机器；这是待确认的外部存储条件，不计作已具备能力。若客户不提供外部存储，仅在同一数据盘保存导出文件，只能帮助处理部分误操作，不能防整机或磁盘损坏。

故障处理顺序：定位并修复原 VM → 必要时由客户重新分配 VM → 从实际可用的数据副本恢复 → 验证应用和数据 → 恢复入口。没有独立副本且原盘损坏时，无法保证数据可恢复。

本版不再承诺“备用环境顶上”、自动切换或 1–4 小时恢复。恢复时间取决于修机/重建和可用备份，数据恢复点取决于实际最后成功副本；未配置、未演练前均不承诺 RPO/RTO。

06 / MCP 与磁盘

境外数据 MCP 与磁盘

  • 客户自行决定同步频率，单个后台任务拉取并落入业务 PostgreSQL，内存计入后台任务的 2GB。
  • 当前协议先比较版本哈希；无变化不下载，有变化分块获取完整新快照，不是逐条记录差异同步。
  • 完整下载与校验后才切换可见版本；失败保留旧版本及客户本地业务记录。大快照必须验证批处理和峰值内存，超出预算时调整任务实现或容量。
  • 客户须提供允许访问 MCP 的 HTTPS／代理／数据交换路径。完全隔离且无交换通道时无法在线同步。
  • 300GB 是数据盘容量，不是内存，也不是全部给 PG：包括 GitLab 仓库、镜像、PG、业务文件和构建缓存。系统盘另计 100GB。
