# GeoAgent 客户内网远程发布方式对比与环境准备清单

编写日期：2026-10-27
目标：研发和交付人员不用去客户现场，通过批准的远程入口提交版本、查看测试、审批灰度和执行回退。
配套：[生产部署、灰度与数据恢复方案](本地部署硬件与境外数据MCP同步方案.md)。

> 最终选型已确定：独立 GitLab＋内网镜像仓库（4 核/8GB）+ 构建测试 Runner（4 核/8GB，单任务并发）+ 独立生产发布 Runner（2 核/4GB）。生产数据库采用两台 PostgreSQL 一主一备，Patroni 管理切换，三成员 etcd 分置 DB01、DB02、OPS01，独立备份保留。下列其他路线与推荐只作为此前的选型比较留档，不覆盖最终决定；尚未实施安装或修改现有 CI。

## 1. 历史选型建议（当前采用 D：GitLab CI + Runner）

- **客户只有普通 Linux 服务器和跳板机，没有成熟发布平台：优先选 A，内网 Ansible 发布机。** 少搭平台，先把构建、测试、部署和回退做成受控任务。
- **希望有网页按钮、历史记录和任务日志：优先选 B，Ansible + Semaphore UI。** 比从零搭一套完整 GitLab CI 更轻，但审批、灰度及回滚逻辑仍要配置和实现。
- **客户已经有 GitLab CI 或 Jenkins：复用已有平台通常最省事。** 新增执行节点和项目权限，不另外建第二套系统。
- **客户已有成熟 Kubernetes 和 GitOps：考虑 E，Argo CD。** 不为了一个项目从零建设 Kubernetes。
- **F 的自制 Webhook 服务组件少，但长期维护责任最大。** 只在已有可复用交付服务时考虑。

“不去现场”允许远程 MFA 登录和线上审批；它不要求取消生产审核。一次提交后，构建、测试及发布执行必须留在客户内网，研发电脑断线不影响任务。

## 2. 六种方式对比

复杂度是相对评价，包含后续维护；以下都可以做到无需到现场，前提是客户提供合法可用的远程通道或自动交换通道。

| 方案 | 怎么触发与执行 | 优点 | 缺点 / 需要补的能力 | 从零建设复杂度 | 适合情况 |
| --- | --- | --- | --- | --- | --- |
| **A. SSH/堡垒机 + 内网 Ansible** | 推代码到内网 Git；远程提交任务；内网控制机运行 playbook | 无需 CI 平台或常驻 Runner；贴合现有跳板机；部署步骤透明 | 报告索引、审批、任务持久化、并发锁和通知需脚本实现；主要面向技术人员 | **较低** | 当前服务器数量不多，先解决远程交付 |
| **B. Ansible + Semaphore UI** | 内网 Webhook 或网页触发模板，后台运行构建/测试/发布任务 | 有任务页面、日志、凭据及模板管理；操作人员更容易使用 | 不是开箱即用的完整 CI；审批和复杂流程受版本/许可影响；灰度测试仍需脚本 | **低至中** | 希望简单、有页面、客户也能操作 |
| **C. Jenkins Pipeline** | 推代码触发 Jenkins，内网 Agent 执行流水线 | 自动测试和多阶段发布成熟，兼容各种部署方式，扩展多 | Java、插件、凭据和 Agent 运维；从零搭建未必更简单 | **中** | 客户已有 Jenkins 或熟悉其运维 |
| **D. GitLab CI + Runner** | 直接推到内网 GitLab，Pipeline 自动构建和测试 | 代码、MR、制品、日志和环境记录统一；与项目现有 CI 方向一致 | 仍需执行节点隔离；部分生产审批功能要相应许可；从零部署完整平台偏重 | **中；已有平台时低** | 客户已有 GitLab，想做长期标准化交付 |
| **E. Argo CD / GitOps** | 构建通过后更新内网发布仓库；集群控制器拉取目标版本 | 生产主动拉配置；版本状态可对账；回退有 Git 记录 | 需要 Kubernetes；不负责镜像构建；自动测试需另配；精细灰度需 Rollouts/流量组件 | **已有平台时中；从零高** | 客户已有成熟 Kubernetes |
| **F. Git Hook/Webhook + 自建任务服务** | 推送事件入持久队列，内网服务按状态机执行脚本 | 界面和平台依赖最少，可完全贴合客户流程 | 幂等、鉴权、防重放、审批、日志、断点、锁和恢复都要自己维护；不能简单 push 后执行 root 脚本 | **初期低、长期高** | 已有受维护的自研交付服务 |

Jenkins Agent、GitLab Runner、Semaphore 执行器和自建任务服务都在承担“有台机器替人执行”的工作。换名字不会消除执行节点；真正可以简化的是平台数量、操作入口和人工搬运步骤。

### 2.1 A：最少平台的路线

```text
本地开发 → 客户批准的远程通道 → 内网 Git
                           → 内网任务控制机（Ansible + systemd）
                               ├─ 构建/测试机：构建、测试、发布镜像
                               └─ 生产受限发布器：灰度、验证、回退
```

Ansible 使用 SSH 管理目标主机，目标应用机不要求安装常驻 Ansible Agent。支持通过 OpenSSH 跳板配置连接。[Ansible 连接说明](https://docs.ansible.com/projects/ansible/latest/inventory_guide/connection_details.html)

本方案让 Ansible 在客户内网管理机运行。研发通过远程入口提交指定 commit/release_id，任务由 systemd 或持久任务服务托管，返回 job_id。不能依赖研发电脑上的长 SSH 会话或只用 `nohup` 当完整发布系统。

固定提供五类任务：构建并测试、部署测试环境、启动生产灰度、扩大灰度、回退。参数只接受已登记版本/环境，不允许操作员上传任意 Shell 片段。日志和状态保存在内网，断线重连按 job_id 查询。

适合先落地；以后同一套 Ansible playbook 可以接到 Semaphore、Jenkins 或 GitLab，不必重写部署逻辑。

### 2.2 B：增加一个简单操作页面

使用 Semaphore 管理任务模板、仓库、主机清单、执行日志。用户在网页选择已经测试通过的版本，再触发允许执行的任务；推代码后自动测试可通过内网认证 Webhook 触发。[Semaphore 官方介绍](https://semaphoreui.com/docs)、[Webhook 集成](https://semaphoreui.com/docs/user-guide/integrations)

需明确：Semaphore 当前文档将 Workflows 标为 Pro，复杂流程、团队权限或审批能力必须按客户选定版本和许可核实，不能当作全部免费已有。可以把基础串行流程封装在 playbook 中；生产放行仍由独立权限控制。[任务模板说明](https://semaphoreui.com/docs/user-guide/task-templates)

构建与生产执行必须隔离：使用所选版本支持的执行隔离，或独立实例/受限发布服务。不要在一个保存生产 SSH 密钥的执行环境中运行任意分支提交的脚本。平台轻量不意味着省掉这条边界。

### 2.3 C：成熟的通用流水线

Jenkinsfile 描述验证、构建、测试部署、验收、生产候选、审批、放量和回退阶段。Jenkins 管理调度，构建及部署放在分开的 Agent 上执行。[Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)、[Agent 架构](https://www.jenkins.io/doc/book/using/using-agents/)

优点是适配性强；代价是插件和执行节点升级、离线插件依赖、流水线脚本维护。已经有 Jenkins 时，这些多数是现有运维成本；从零搭建时，它不一定比 GitLab Runner 更省事。

### 2.4 D：代码与发布统一

代码推到客户内网 GitLab，项目流水线自动运行。优先复用现有 GitLab Registry，避免再维护重复镜像仓库。[GitLab Registry](https://docs.gitlab.com/user/packages/container_registry/)

普通构建 Runner 不持有生产凭据。生产 Runner 单独管理，只接受客户批准的发布控制项目或受保护来源，使用固定且受审核的部署程序；不把任意源码分支的 CI 脚本直接带进生产执行环境。[Runner 安全说明](https://docs.gitlab.com/runner/security/)

GitLab 的 Protected environments 和 Deployment approvals 在当前官方文档中属于 Premium/Ultimate。Free 版可以用受限发布项目、受保护分支/标签及手动任务组合，但需要额外实施角色隔离，不能把单个 `when: manual` 按钮当成独立审批体系。[环境权限](https://docs.gitlab.com/ci/environments/protected_environments/)、[部署审批](https://docs.gitlab.com/ci/environments/deployment_approvals/)

现有仓库 CI 固定了原 Sealos 发布目标；客户接入需新建客户部署配置。不能直接复用原集群凭据或把所有目标环境混在同一组变量中。

### 2.5 E：生产自己拉取已批准版本

代码仓库存源码，发布仓库存已验收镜像 digest、环境配置与目标副本数。生产 Argo CD 从内网发布仓库拉配置，研发不需要直接访问 Kubernetes API。[Argo CD 架构](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/)

Argo CD 不负责构建镜像，也不会因为“自动同步”就自动完成业务测试。灰度放量需要匹配的 Argo Rollouts、入口流量控制和指标分析；普通 Deployment 滚动更新不是按用户灰度。[Argo Rollouts 灰度](https://argo-rollouts.readthedocs.io/en/stable/features/canary/)

回退需要同时修改发布仓库的期望版本，不能只在集群里手工改旧镜像，否则自动同步可能重新应用错误版本。[Argo CD 自动同步](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)

### 2.6 F：只在可承担自研运维时选择

最小正确架构也需要：认证 Webhook、持久队列、版本白名单、任务状态、发布互斥锁、受限执行用户、测试门禁、审批记录、日志、失败重试和回退。

Git Hook 只负责把“哪个仓库、哪个 commit”入队，然后返回；不能在 `post-receive` 中同步构建几十分钟，也不能将提交消息或分支名拼接成 Shell 命令。任务重启后要能继续或安全结束。相比直接维护成熟工具，长期成本很可能更高。

## 3. 代码推哪里：把跳板机变成通道

### 3.1 优先使用客户内网 Git

```text
研发电脑
  └─ 批准的 VPN / 堡垒机 / SSH 跳板
       └─ git.customer.example：客户项目仓库
            └─ 内网发布系统拉取指定 commit
```

客户可以提供 GitLab、Gitea 或已有企业 Git 服务；发布平台不必和代码仓库绑定。只要能通过批准通道推 Git，Ansible/Jenkins/Semaphore 都能拉取内网仓库。

暂时没有 Git 平台时，可由客户提供受限裸仓库作为代码落点，先接 A；生产发布仍应对版本和审批单独登记。不要把“直接登录生产 `git pull`”作为发布流程。

下面只是客户允许标准 SSH ProxyJump 时的连接模板；尚未配置或连接任何客户环境：

```sshconfig
Host customer-jump
    HostName bastion.customer.example
    User customer_assigned_user
    IdentityFile ~/.ssh/customer_jump_key
    IdentitiesOnly yes
    ForwardAgent no

Host customer-git
    HostName git.customer.example
    User git
    ProxyJump customer-jump
    IdentityFile ~/.ssh/customer_git_key
    IdentitiesOnly yes
    ForwardAgent no
```

仓库地址示例：

```text
git@customer-git:delivery/geoagent.git
```

主机指纹由客户确认后固定；私钥不复制到跳板机，不开启 SSH Agent 转发。ProxyJump 需要客户允许到 Git 的 TCP 转发；它不是绕过堡垒机策略的方法。[OpenSSH ProxyJump](https://man.openbsd.org/ssh_config#ProxyJump)

### 3.2 跳板机不同能力，对应不同接入

| 客户现有入口 | 建议接法 | 自动化边界 |
| --- | --- | --- |
| VPN + 标准 SSH | 直接到批准的内网 Git/发布入口 | 最方便；仍需用户与机器权限分开 |
| 支持 ProxyJump 的 SSH 堡垒机 | 经跳板推 Git、访问发布入口 | 远程连接允许 MFA，后续任务在内网持续执行 |
| 只有审计终端/浏览器堡垒机 | 使用客户支持的 Git/文件代理、远程桌面或发布门户 | 不能假设 SCP、端口转发或机器密钥可用 |
| 只允许远程桌面到跳板机 | 在该桌面提交代码/操作内网发布页面 | 人仍不用到现场，但不保证本地直接 `git push` |
| 业务区只出不进 | 内网执行器拉取批准的交换区仓库或制品 | 无需对公网开放生产服务器，但拉取通道必须获准 |
| 完全隔离无交换通道 | 客户批准离线摆渡后在内网自动执行 | 无法实现从外部无人送入新版本 |

运行系统本身可以完全留在内网；远程操作只需要到代码入口、发布门户、测试预览和报告。不需要研发长期持有生产 root、数据库超级用户或直接访问所有机器。

## 4. 一次发布的理想操作体验

1. 开发人员在本地提交代码，推到客户仓库的开发/评审分支。
2. 内网系统自动校验代码、构建镜像、运行后端/前端测试；失败即停止。
3. 合入已批准分支后，自动将构建成功的同一 digest 部署测试环境。
4. 自动跑 API、浏览器、MCP 同步及基础性能用例，生成 JUnit/HTML、失败截图和日志；开发人员通过远程门户查看。
5. 指定人员从远程测试入口确认业务用例，选择“进入生产候选”。候选启动但不接普通流量。
6. 客户授权人在线审批，先开放白名单用户，指标满足后逐步放量。放量可以按既定规则自动执行，不需要操作员逐台登录。
7. 失败时停止放量；满足回退条件则恢复旧稳定组，保存结果。数据库恢复是独立操作，不随代码回退自动执行。
8. 发布完成显示环境、commit、digest、schema、测试结果、操作人、耗时和可回退版本。

首次安装阶段也尽量由客户先开通远程管理与基础主机，我们远程完成。若客户只有现场管理员能安装远程入口，第一次基础开通仍需客户配合；之后日常发布不应要求现场值守。

## 5. 所有方案共用的自动化底座

选 A/B 不代表只准备一个 `deploy.sh`。下列逻辑应只实现一套，由不同平台调用。

| 模块 | 必须具备的行为 |
| --- | --- |
| 制品构建 | 在内网构建指定 commit，生成不可变镜像 digest；保存依赖版本、测试报告和来源 |
| 制品传递 | 测试、生产使用同一 digest；镜像仓库在内网，节点直接拉取 |
| 任务持久化 | 返回 job_id；状态、日志、退出码持久保存；电脑断线不中断 |
| 测试隔离 | 测试专用 PG、临时数据及凭据；不得连生产库 |
| 生产授权 | 可提交代码不等于可发布生产；客户批准的是具体 release_id/digest |
| 执行隔离 | 不可信/普通分支构建环境不能读取生产密钥，也不能直连生产 |
| 发布互斥 | 每环境同一时间只允许一个发布/回退；防止过期任务覆盖新版本 |
| 部署幂等 | 只部署指定已批准版本；重跑能识别已完成阶段，不重复迁移或清库 |
| 数据库变更 | 独立迁移账号、迁移锁、schema 兼容检查；禁止每个副本启动时抢着改表 |
| 灰度门禁 | 保留新旧实例、固定用户分组、指标门槛、暂停/回退 |
| 回退 | 明确上一版本及当前归属；回退镜像、路由和兼容配置，保留业务数据 |
| 报告留存 | 测试报告至少 90 天，发布/审批/回退记录建议 180 天；按客户要求调整 |
| 制品保留 | 至少当前版本和最近 5 个已发布版本，建议 90 天；回退窗口内禁止清理依赖镜像 |

若选择 GitLab，`resource_group` 可用于串行化同环境任务，但仍应检查版本归属和旧任务覆盖风险。[GitLab CI 配置](https://docs.gitlab.com/ci/yaml/#resource_group)

构建机故障应影响新发布，不影响线上服务。发布系统重启后必须先核对线上版本与任务阶段，再决定继续或结束，不能重新盲目执行全流程。

## 6. 内网构建：避免每次人工搬镜像

### 6.1 能受控出站

建立客户内网镜像仓库及包缓存，由批准的代理/镜像同步服务更新。构建任务只访问这些内网地址；生产节点只拉内部制品，不访问公网 npm、PyPI、Docker Hub。

只维护允许使用的基础镜像与依赖，锁定版本和 digest。新增依赖在测试/构建阶段完成批准和同步，不能等生产发布时临时联网安装。

### 6.2 完全不允许出站

首次准备并通过客户摆渡流程导入：

- 匹配客户 CPU 架构的 Node 22、Python 3.12、数据库和发布工具镜像。
- `package-lock.json` 对应的 npm 包及浏览器测试依赖。
- 锁定的 Python 直接/间接依赖、适用平台 wheel、系统 apt 包及依赖闭包。
- 内部 CA、测试浏览器运行镜像、Ansible collections/roles；选择 Jenkins 时还包括插件及依赖闭包。
- 校验清单、来源信息、必要签名和可离线使用的安全扫描数据。

之后普通代码修改只需推代码，内网复用依赖构建。新增依赖、基础镜像更新或插件更新仍需要批准同步，这是完全离线场景的正常维护环节。

本项目现有 Dockerfile 中 `npm ci`、Python 安装和 apt 更新仍依赖包源；需接内网镜像。`requirements.txt` 当前为版本范围，交付管线应补依赖锁定，不能只固定代码 commit 就声称可复现。现有 Dockerfile 的 `DEBIAN_MIRROR`/`PYPI_INDEX_URL` 可作为改造基础；npm 和基础镜像也需同步处理。

内网源码构建实在不被允许时，使用外部已构建且签名的 OCI 制品，经批准渠道进入内网 Registry，再自动部署测试。这是备选方案：省构建环境，但每个版本的镜像仍需经过摆渡。

## 7. 客户需要提供的机器和权限

### 7.1 A/B 轻量路线的额外资源

不包含主方案中的应用、数据库和测试环境；以下为起步估算，优先复用已有服务。

| 资源 | 起步建议 | 是否可复用 |
| --- | --- | --- |
| 内网构建/测试执行机 | 4 vCPU / 8GB / 200–300GB SSD，单任务并发 | 可复用已有构建资源；不能放生产凭据 |
| 发布控制机 | 2–4 vCPU / 4–8GB / 80GB SSD | 运行 Ansible/任务服务；选 B 可放受限部署 UI，构建执行仍隔离 |
| Git 服务 | 优先客户现有 Git | 没有时可用轻量 Git 或受限裸仓库；不是必须新建 GitLab |
| 内网 Registry | 优先已有；新建可从 2–4 vCPU / 4–8GB / 200GB 起 | 小规模可与独立构建平台配套，但不能因此获得生产权限 |
| 依赖仓库 | 现有包代理；或为构建区预留 200–500GB | 容量按依赖、浏览器镜像和保留版本测量 |
| 跳板机/远程门户 | 复用客户现有 | 不在跳板机上跑高负载构建或保存生产万能密钥 |

A/B 使用已有 Git、Registry 和跳板机时，通常新增 **1 台构建机 + 1 台受限发布控制机** 即可开展建设。平台自身业务状态也需备份；单机发布平台中断只影响交付，不应影响已经运行的应用。

GitLab/Jenkins 路线优先由客户现有平台提供相应执行资源，不重复采购。没有现有平台又选择完整自建时，另预算控制服务、Git/Registry、依赖库、构建执行与生产执行；不能把“装一个 Runner”当成全部平台成本。

### 7.2 网络开通申请

| 方向 | 建议端口 | 用途 |
| --- | --- | --- |
| 研发 → 客户远程入口 | 由客户规定的 VPN/堡垒机协议 | MFA、账号审计 |
| 跳板/批准代理 → 内网 Git | SSH 22 或 HTTPS 443 | 提交/拉取代码 |
| 远程入口 → 发布门户/测试预览/报告 | HTTPS 443 | 远程查看及审批；可通过受控 Web 代理 |
| 构建机 → Git/Registry/依赖库 | HTTPS 443，Git 可用 SSH | 取代码、依赖及推镜像 |
| 内网 Git → 任务入口 | 内网 HTTPS | 可选认证 Webhook；也可由执行器定期拉取 |
| 测试执行器 → 测试入口/测试部署目标 | HTTPS 443、必要 SSH 22 | 部署、浏览器/API 测试 |
| 发布控制机 → 生产应用/网关 | 受限 SSH 22 或平台 API | 指定版本部署、调整流量、回退 |
| 应用节点 → 内网 Registry | HTTPS 443 | 拉取批准镜像 |
| 发布迁移任务 → PG 主库路由 | TLS 5432 | 仅短时受限迁移任务 |
| 所有服务器 → 内网基础服务 | DNS/NTP/CA/日志端口 | 解析、时间、证书和审计 |

并不要求全部方向从研发电脑直通。堡垒机是人员入口；自动化执行器应位于客户批准的管理网，拥有限定到目标机的通道。若所有机器操作都强制逐次人工输入 OTP，客户需提供合规的机器执行身份或受控部署 API，否则只能远程人工操作，不能无人值守执行。

### 7.3 权限分工

| 角色 | 需要的权限 | 不应混用 |
| --- | --- | --- |
| 开发人员 | 提交开发分支、查看报告、访问测试、申请生产发布 | 默认无生产机器管理员、PG 超级用户权限 |
| 代码审核人 | 审核合入、确认版本范围 | 不自动拥有全部生产操作权限 |
| 构建执行身份 | 读取代码、访问内部依赖、推候选镜像、操作测试环境 | 不持有生产凭据 |
| 客户发布审批人 | 批准具体 release_id/digest 及灰度范围 | 审批不能只批准一个会继续变化的分支名 |
| 生产执行身份 | 运行受审核的部署模板、调整网关、有限重启/回退 | 不执行普通分支任意脚本，不开放任意 sudo |
| DBA/恢复负责人 | 迁移授权、数据库切换和备份恢复 | 常驻应用账号不得复用该身份 |

生产控制程序与审批清单由客户受保护的发布仓库/管理账户维护。应用仓库中待评审的提交不能自行改生产门禁然后立刻获得执行权。

## 10. A / B / C / D 从零建设的工期与难度

### 10.1 估算口径

以下是结合本项目和客户内网要求的工程估算，不是软件官方工期或固定交付承诺。

- 按一名熟悉 Linux、Docker、SSH 和自动化发布的工程师全职实施，项目开发人员配合接口及测试问题。
- 客户已提供可用服务器、生产/测试基础环境、域名、证书和批准的远程通道；客户采购、账号审批、网络开通等待时间另计。
- 发布平台及部署脚本从零建设；可复用本项目已有 Dockerfile、Python/前端测试和 CI 结构。
- 包含单项目的基础代码/制品落点接入、测试部署、报告、生产授权、灰度编排、回退和交接。初始依赖可以获取；完全离线依赖准备另计。
- 不包含 GeoAgent 的 SQLite→PostgreSQL 迁移、应用共享状态改造、客户 MCP 接收器开发，以及整套生产数据库 HA/灾备基础设施新建。它们是并行建设项和生产验收前置条件。
- 1 人日约为一名工程师一个工作日的有效工作量。表中是各里程碑的累计投入，不把三列相加；两人参与也不能简单将历时减半。

| 方案 | 工具/平台装好 | 首次自动完成构建→测试→测试部署 | 可交付生产发布流程 | 难点分布 |
| --- | --- | --- | --- | --- |
| A：Ansible + 内网任务控制 | 0.5 人日左右 | 2–4 人日 | **7–12 人日，约 1.5–2.5 个工作周** | 安装容易；可靠任务执行、门禁和审计要自己编排 |
| B：Semaphore + Ansible | 0.5–1 人日 | 3–5 人日 | **8–14 人日，约 2–3 个工作周** | 页面配置容易；部署脚本、执行隔离及审批衔接是主要工作 |
| C：Jenkins | 1–2 人日 | 3–6 人日 | **10–18 人日，约 2–4 个工作周** | Controller/Agent、插件、凭据边界和 Pipeline 联调 |
| D：GitLab CI/CD | 1–2 人日 | 3–6 人日 | **10–18 人日，约 2–4 个工作周** | GitLab/Registry/Runner、证书及权限，生产发布隔离 |

“工具装好”只表示平台能启动、登录或执行基础命令；不表示已具备可回退的生产发布。完整阶段还需要多次故意失败的演练，包括测试失败不发布、候选异常停止放量、旧任务不覆盖新版本、执行器重启、远程会话断开和应用回退。

### 10.2 A：安装最轻，流程责任主要在脚本

要做的工作：

1. 在内网控制机安装 Python/Ansible，建立测试与生产主机清单，配置受限 SSH 账号与主机指纹。
2. 接入内网 Git、镜像仓库和构建机；按指定 commit 构建，不使用随时变化的分支内容直接发布。
3. 写 playbook：准备目录、分发配置、拉取 digest、启动候选、检查健康、切换流量、回退。
4. 用 systemd/受控任务入口在内网托管任务，持久记录 job_id、状态、日志和退出码。
5. 补发布锁、审批版本记录、失败退出、重试幂等和恢复后对账；输出可远程读取的测试报告。

Ansible 控制节点可通过 SSH 管理目标节点，无需为普通 Linux 目标安装常驻 Agent；这降低安装负担，但不会自动提供完整 CI 门禁。[Ansible 安装与架构](https://docs.ansible.com/projects/ansible/latest/installation_guide/intro_installation.html)

难度评价：基础安装低，生产脚本中等，完整审批和审计做到好用后可能升至中高。最容易漏的是“上次执行到一半失败，重新执行会不会重复迁移/覆盖新版本”和“SSH 断开后还能否准确查询任务”。

日常体验：技术人员提交版本后，通过远程命令或受限任务入口发起测试/发布，按任务号查看报告。对不熟悉命令行的客户，易用性弱于 B/C/D。

维护成本：平台升级负担较低；部署逻辑、状态记录和审批脚本由项目团队持续维护。适合少量项目、固定交付人员、流程相对简单的情况。若未来要补完整的图形化流程、权限管理和报表，应考虑接 B/C/D，避免继续自建平台。

### 10.3 B：保留 Ansible，加上可操作的页面

要做的工作：

1. 完成 A 中可复用的构建、测试、灰度和回退 playbook。
2. 安装 Semaphore，配置 HTTPS、持久化存储、备份、用户及仓库连接。
3. 建立构建测试、测试部署、生产候选、放量和回退模板，限制环境与版本参数。
4. 配置内网认证 Webhook，使指定分支/版本的提交触发测试；生产操作使用独立权限或受限发布服务。
5. 实现测试成功与发布资格的关联，禁止手工选择未通过测试的 digest；验证失败、重跑、断线及平台重启行为。

Semaphore 可用二进制或容器等方式部署；模板可把仓库、主机清单和变量组合为可执行任务。[安装方式](https://semaphoreui.com/docs/admin-guide/installation)、[模板说明](https://semaphoreui.com/docs/user-guide/task-templates)

难度评价：中等。安装 UI 通常不慢，主要工作仍是 Ansible 脚本。当前文档中的 Workflows 为 Pro，因此是否购买、如何实现生产审批和构建/生产执行隔离，应在开工前确定，避免后面返工。

日常体验：推代码后自动跑测试，客户通过网页看状态、日志及报告；授权人员选择通过测试的版本，点击指定发布模板。比 A 更适合交给客户自己使用。

维护成本：需要维护平台数据、凭据保护、版本升级及 playbook；通常比自制任务页面省事。**若 A 的脚本已经成熟，再接入基础网页模板及日志通常额外约 1–3 人日**，复杂审批和隔离另算，不必重新投入完整的 8–14 人日。

### 10.4 C：Jenkins 的平台能力强，但离线运维较多

要做的工作：

1. 安装受支持的 Jenkins/Java 组合，配置 HTTPS、账号、持久化与备份。
2. 配置构建、测试和生产发布执行环境；普通构建不在持有生产凭据的节点运行。
3. 安装尽量少的必要插件，配置代码触发、仓库凭据、测试报告和通知。
4. 编写 Jenkinsfile，组织验证、构建、测试部署、自动验收、生产候选、审批、放量与回退。
5. 处理 Pipeline 超时、重跑、执行节点离线、控制服务重启、并发发布和制品过期。

Jenkins 的控制服务负责调度，Agent 执行任务；实际架构通常需要这些角色及其通信配置。[Jenkins Agent 说明](https://www.jenkins.io/doc/book/using/using-agents/)

难度评价：中高。难点通常不在启动 Jenkins 页面，而在插件依赖、执行节点、凭据隔离和流水线失败行为。完全离线时，插件本身及其依赖需要一起准备，升级也要验证兼容性。[Jenkins 安装入口](https://www.jenkins.io/doc/book/installing/)

日常体验：代码推送自动触发流水线，开发人员能看阶段、日志和报告；生产在指定阶段等待授权。对“多个阶段自动跑、失败定位、多人协作”比裸 Ansible 更方便。

维护成本：四种中偏高，主要是 Java/Jenkins/插件/Agent 的升级和兼容。客户已有 Jenkins 管理团队时，这个负担大部分已经存在，此时应优先复用，不必为了少装一个 Agent 换平台。

### 10.5 D：GitLab CI/CD 将代码与发布放在一个入口

要做的工作：

1. 安装内网 GitLab，设置域名/TLS、仓库、用户、备份和内网 Container Registry。
2. 配置构建/测试 Runner 与受限生产发布执行环境，确定 executor 及容器构建方式。
3. 迁入代码，配置分支、标签、CI 变量和凭据范围；验证跳板机推代码及浏览器查看结果。
4. 改造 `.gitlab-ci.yml`，接入自动测试、不可变镜像、测试环境、报告和生产发布阶段。
5. 设置发布互斥、过期任务保护、生产授权、灰度与回退，测试制品保留及平台备份恢复。

GitLab 负责仓库与流水线管理，Runner 才是实际执行构建、测试和部署任务的程序，两者缺一不可。[GitLab Runner 说明](https://docs.gitlab.com/runner/)

难度评价：中等至中高。全新 GitLab 涉及服务、存储、TLS 和备份，资源成本比 A/B 高；本项目按用户确认的 4 vCPU/8GB 部署 GitLab＋Registry，独立构建测试 Runner 同为 4 vCPU/8GB、并发任务数 1；这是本项目的起步预算，需按锁定版本的安装要求配置并验证峰值资源，不作为通用容量保证。[GitLab 安装要求](https://docs.gitlab.com/install/requirements/)

日常体验：提交代码、评审、测试报告、制品、环境和发布记录集中在一个系统，客户后续接其他项目也容易复用。项目已有 GitLab CI 与 Dockerfile，能够复用验证和制品处理的部分思路，但原 Sealos 部署目标、SQLite 备份和单副本方式仍需替换。

维护成本：需要维护 GitLab、数据库/仓库/Registry 存储、Runner 和升级路径。相较 A/B，平台更重，但减少自建代码管理与报告关联的工作。原生生产环境审批涉及 Premium/Ultimate；Free 版方案需另做受限发布项目或等效授权边界。[GitLab 部署审批](https://docs.gitlab.com/ci/environments/deployment_approvals/)

### 10.6 哪些因素会显著改变工期

| 条件 | 估算影响 | 说明 |
| --- | --- | --- |
| 客户已有成熟 GitLab CI/Jenkins、可用执行器和 Registry | 单项目接入可按约 4–8 人日重新评估 | 不重复建设平台；具体仍取决于项目脚本和权限 |
| A 的部署脚本已成熟，只增加 B 的基础操作页面 | 约增加 1–3 人日 | 审批升级、许可证采购及执行隔离变更不包含 |
| 完全离线且没有任何依赖镜像 | 可能额外增加 3–8 人日技术准备 | npm/wheel/apt/基础镜像/测试浏览器/插件闭包；摆渡审批等待另算 |
| 新增企业 SSO、复杂审计或多级审批 | 另行估算 | 与客户身份系统及许可能力有关 |
| 堡垒机不支持 Git/文件转发，只有交互终端 | 先做接入验证，不能直接承诺工期 | 可能需要客户提供内部开发桌面或文件交换入口 |
| 工程师不熟悉所选平台 | 上述区间不再适用 | 需另计学习、试错和客户环境适配 |
| 应用仍不支持多实例/PG | 生产发布验收无法完成 | 可先建设管线，但不能把平台安装完成当成项目可上线 |

完全离线额外投入与平台准备可能部分重叠，不能机械相加。客户账号/网络审批的等待时间没有可靠统一天数，应作为项目计划中的独立依赖项跟踪。

### 10.7 对本项目的选择建议

- 只交付这一个项目、希望维护简单、客户也能看页面：倾向 **B**，提前确定版本许可及生产审批方式。
- 先打通远程交付，日常由技术人员操作：选 **A**，之后可以接 B。
- 客户已有 Jenkins：选 **C**，优先沿用其账号、执行节点和运维体系。
- 客户准备长期管理多个项目，代码与发布都要规范化：倾向 **D**；现有 GitLab 可直接复用时，D 的投入通常更有优势。

四种方案都能实现人员不去现场。实际成败首先取决于客户能否提供代码入口、内网执行资源、生产受限发布通道和远程结果查看能力，其次才是采用哪个平台。
