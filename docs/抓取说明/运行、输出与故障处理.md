# 运行、输出与故障处理

## 1. 环境准备

```bash
cd /Users/yujunjun/opensource/GeoAgent
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm ci
```

可选环境变量写在仓库根目录 `.env`，不要提交 `.env`：

```dotenv
# 采集输出根目录；默认是 data/collector-output
COLLECTOR_DATA_ROOT=/absolute/path/to/runtime-output

# 应用读取的数据根目录；设置后优先于默认回退逻辑
CRAWLER_ROOT=/absolute/path/to/runtime-output
```

`COLLECTOR_DATA_ROOT` 控制统一运行器写入的位置，`CRAWLER_ROOT` 控制应用导入的位置。生产或测试环境应明确设置，避免“采集写在 A、应用读在 B”。

## 2. 推荐运行入口

### 查看采集器

```bash
.venv/bin/python scripts/collect.py --list
```

### 单个采集器

```bash
.venv/bin/python scripts/collect.py --id xinhua-monitor
```

可重复指定 `--id`，例如：

```bash
.venv/bin/python scripts/collect.py \
  --id readiness-monitor \
  --id diplomacy-monitor \
  --timeout 900
```

### 按主题运行

```bash
.venv/bin/python scripts/collect.py --topic usiran
.venv/bin/python scripts/collect.py --topic ukraine
```

### 全量运行

```bash
.venv/bin/python scripts/collect.py --all --timeout 900
```

每个采集器在独立子进程中运行。成功后，统一入口把 `collectors/<id>/output/` 同步到 `data/collector-output/<id>/output/`，并把本轮结果写入：

```text
data/collection-runs/<UTC时间>/results.json
```

### 只做注册表提供的自检参数

```bash
.venv/bin/python scripts/collect.py --id readiness-monitor --verify-only
```

没有注册 `selftest_args` 的采集器会返回 `not_provided`。这不是抓取成功，也不是质量验证通过。

## 3. 旧批量刷新脚本

`scripts/refresh_crawlers.py` 是历史批量流程：最多 3 路并发，按“selftest → collect → verify”执行，并额外运行市场补充。它依赖采集器内部的 `tools/rerun_batch.py`、`verify_report.py` 或 `verify_numbers.py`，不是所有当前仓库副本都具备这些文件。

使用前先检查：

```bash
test -f collectors/tools/rerun_batch.py
find collectors -path '*/tools/verify_report.py' -o -path '*/tools/verify_numbers.py'
```

如果依赖不完整，使用 `scripts/collect.py` 单个或按主题运行，并按照采集器 README 单独执行验证。

后续维护应确定一个生产批量入口。两套入口的并发、验证和报告格式目前不完全一致，不能把其中一套的成功结果当成另一套的证据。

## 4. 输出目录和文件含义

```text
data/collector-output/<id>/output/
  ALL-records.jsonl       跨运行累计记录，供适配器优先读取
  LATEST-records.jsonl    最近窗口记录；没有 ALL 时可作为回退
  geo-v6.json             统一扩展协议，记录和指标一起输出
  LATEST.md               人读日报或快照说明
  _source_status.json     来源状态（如果采集器提供）
  _fetch_stats.json       本轮请求统计（如果采集器提供）
  _filter_audit.json      被过滤候选的审计记录（如果采集器提供）
```

应用读取时会把输入文件按内容归档到 `data/archive/`，然后生成不可变快照到 `data/research.sqlite3`。这些运行数据都被 Git 忽略。

## 5. 导入应用快照

启动后：

```bash
curl -s http://127.0.0.1:8000/api/status
curl -X POST http://127.0.0.1:8000/api/import
```

UI 的“更新快照”执行同一条导入路径。导入失败时不会把半成品快照当作成功结果；相同输入会复用内容哈希快照，内容变化会产生新快照，旧快照保持不变。

如果没有真实输出，状态接口中的 `crawler_root` 会显示 `examples/demo-data`。这表示当前服务在演示数据上运行，不表示采集器刚刚成功抓取。

## 6. 故障定位顺序

### 页面显示 Demo 数据

1. 检查 `curl -s http://127.0.0.1:8000/api/status` 的 `crawler_root`。
2. 检查 `CRAWLER_ROOT` 是否指向包含 `<id>/output/` 的目录。
3. 检查输出中是否有 `ALL-records.jsonl`、`LATEST-records.jsonl`、`geo-v6.json` 或 TACO 文件。
4. 重新执行 `/api/import`，记录返回的快照 ID 和错误。

### 采集器返回 0，但没有记录

检查：

- 运行报告中的 `stdout_tail`、`stderr_tail`；
- 采集器自己的 `_fetch_stats.json` 和 `_source_status.json`；
- `output/` 是否写在了源码目录而不是 `COLLECTOR_OUTPUT_ROOT`；
- 是否是“请求成功但筛选为空”，不要把它标成网络失败。

### 403、502、超时

保留原始状态和最后成功时间，按采集器 README 的代理、重试和备用信源规则处理。不要把代理端口写死到源码中，也不要通过绕过风控来提高命中率。请求失败不能删除上一份成功输出。

### 导入报错

先查看 `data/archive/` 中对应原始文件和错误文件/行号，再检查：

- JSONL 是否存在坏行；
- `geo-v6.json` 的 `schema_version` 是否为 `geo.v6/1`；
- `source_ids` 是否指向同一适配器中的记录；
- 指标日期、单位、数值和重复日期是否符合协议；
- 坐标是否在合法范围，是否包含 `precision` 与 `evidence_text`。

## 7. 运行后的质量检查

```bash
# 只读审查当前快照和本地输出，不重新抓取
.venv/bin/python scripts/audit_crawlers.py

# 运行仓库测试和前端构建
.venv/bin/python -m pytest -q
npm run build
```

完整质量结论应同时说明：请求状态、过滤状态、字段清洗、去重数量、时间完整性、翻译覆盖、来源核验和指标口径。自检通过只证明代码/输出满足自检条件，不证明外部事实全部正确。
