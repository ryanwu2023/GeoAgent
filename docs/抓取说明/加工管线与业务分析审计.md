# 加工管线与 UI 数据业务分析审计

更新时间：2026-10-01（Asia/Shanghai）

## 1. 审计范围与结论

本审计把“加工”拆成两层核对：

1. **数据基础加工**：采集器输出、同步、读取、原始归档、规范化、专用适配器、去重、快照和 API 投影。
2. **数据业务分析**：主题/维度筛选、指标比较、条件传导、情景假设、问答、简报、翻译、人工核验和 UI 交互。

结论是：`docs/抓取说明/加工管线逻辑分析.md` 描述的第一层主链路与代码**大体匹配**，但不是本项目的全部数据业务分析，也不是“采集成功”的证明。业务分析从快照之后才开始，且当前实现是“可追溯证据 + 程序规则 + 可选模型增强”，不是自动事实核验或因果预测。

### 4.1 风险监测、证据台账和数据源

- `src/App.tsx:160-196` 按 `snapshot_id/topic/dimension/start/end` 请求 workspace，并缓存 60 秒。
- 地图收到 `present_map_record` 的轻量记录，点位是文章提及/区域参考信息；它是线索空间索引，不是实时部署图或冲突强度热力图。
- 证据台账通过 `/api/evidence` 每次加载 30 条，服务端搜索原文、中文译文、来源和发布者；点击后 `/api/evidence/{id}` 才取完整正文、抽取信息和链接健康。
- `coverage` 统计的是被主题/维度分类的记录。当前快照总记录 4384 条，而美伊、俄乌主题计数分别为 2279、1251，剩余记录可能是背景资料或未命中主题；不能把页面主题计数当成全量采集覆盖量。
- 来源面板展示项目、来源状态和归档文件。后端统一吸收 `_source_status.json`，没有该文件时读取 `_fetch_stats.json`；某些采集器的 `_source_health.json` 需要直接检查，不能假定已经进入 UI。
- 轻量投影仍有规模边界：本次实测 `usiran` 的 `/api/workspace` 约 2.5 MB，一次返回 2301 条地图记录（coverage 统计为 2279 条非 supplemental 主题记录）；同一主题 `/api/evidence?limit=30` 约 36 KB。也就是说，正文没有塞进地图是有效优化，但 workspace 仍未按地图视窗、聚合或分页裁剪，前端展现效率的下一瓶颈就在这里。

### 4.2 量化指标与资产矩阵

`backend/research.py:39-59` 从 `snapshot["observations"]` 按主题序列筛选、别名去重，再计算 current、previous、delta、pct 和 freshness。`backend/workbench.py:26-47` 以日 7、周 14、月 45 的默认阈值判定可用性，并按主题优先级挑选重点指标。

`analysis()`（`backend/research.py:76-117`）的顺序是：

1. 用关键词为资产和情景找候选记录；候选只标为“待核验线索”，不自动成为支持证据。
2. 将可比且新鲜的市场观测加入资产卡片；UI 明确写“同期观测，不构成因果验证”。
3. `assessment.enrich` 根据数值方向生成条件性方向标签；不生成价格目标、收益预测或冲突因果结论。
4. `topic_paths` 取近 14 日的非结构化记录，补充传导渠道、成立条件、反证和下一观察项，最多放 3 条候选证据。
5. 三个情景是研究假设，不计算发生概率；每个情景都带数据需求和缺口。

所以“加工后的 4384 条记录”不会直接变成“资产利好/利空”。资产业务使用的是快照中的结构化观测、主题候选和规则版本的组合结果。

### 4.3 智能问答与 PiChat 边界

`backend/research.py:153-264` 的问答链路是：锁定快照和日期范围 → 关键词/中文二字片段检索 → 程序计算指标事实 → 如问题涉及资产、情景或简报则追加规则分析 → 保存答案及引用。

只有同时满足 `use_model=true`、模型已配置且存在引用时，才调用 `backend/llm.py` 的 PiChat 或兼容 Chat Completions。模型输出必须引用已有证据 ID，不能新增数字、概率、价格目标或收益预测；调用失败会保留本地结果并记录缺口。连续追问也不是 PiChat 服务端会话，而是读取本地 `previous_answer_id`，把上一问拼接成追问。

因此当前项目的“智能问答”是证据约束的检索/计算/可选模型增强，不是让 PiChat 直接访问爬虫目录，也不是由模型替代清洗和事实核验。

### 4.4 简报、翻译与人工复核

- `/api/briefs` 使用完整快照，不受当前页面日期筛选限制；`create_brief()` 先按两个主题生成近七日 takeaway，再加入问答结果、资产矩阵、情景和数据缺口，保存到 SQLite，可下载和做版本 diff。它不是把全量采集表直接导出成统计报告。
- `present_map_record`、`present_record_summary`、`present_record` 分别服务地图、列表和详情。中文翻译是缓存/后台任务或按记录手动触发的展示层能力，原文仍保留；机器译文通过术语和质量检查后才替换展示文本。
- `/api/reviews/{rid}` 与 `/api/reviews/{rid}` POST 以快照、记录和版本保存研究员的升级/持续/缓和/待研判判断。该结果覆盖 UI 展示分类，但不改写采集原文和不可变快照。
- UI 的问答历史只按主题和维度过滤，未按当前 start/end 再过滤（`src/App.tsx:240-258`）；这会让回放列表出现同主题不同日期范围的旧答案，是当前业务体验上的边界。
- 快照本身不可变，但模型问答成功后的资产/情景 assessments 会写入 `analyses`，`workspace` 后续读取时可能覆盖同一快照的基础规则结果；因此要区分“原始数据快照不变”和“业务分析投影可更新”。

## 5. “加工”是不是本项目数据业务分析的全部？

不是。可以用下面的边界判断：

```text
采集器与来源覆盖
  → 数据基础加工（本文原加工管线）
  → 快照与可追溯存储
  → UI 投影与检索
  → 主题/指标/资产/情景规则分析
  → 问答、简报、翻译、人工复核
  → 可选 PiChat 增强与研究交付
```

原加工管线解决的是“数据能否被稳定读取、追溯、合并和服务”；它没有独立解决：

- 来源是否覆盖完整、来源级 403/超时是否被修复；
- 关键词分类是否为真实事件、地点是否为实际部署；
- 指标是否具有可比口径、时效是否足够、市场变化是否由冲突造成；
- 研究员对证据的核验、冲突信息处理和版本化判断；
- 问题理解、答案引用、简报组织和 PiChat/模型调用；
- UI 的筛选、分页、缓存、翻译状态、历史回放和用户交互。

因此，当前“加工”是数据业务分析的必要基础，但不是全部。若项目目标是可运行的小 demo，当前链路已经能把真实采集输出导入快照并在 UI 展示；若目标是生产级业务分析，还需把来源健康、新鲜度、口径/证据核验和问答历史范围继续做成可观测、可审计的闭环。

## 6. 业务层详细说明

### 6.1 业务对象不是同一种“数据”

| 业务对象 | 来源 | 业务含义 | 是否可直接下结论 |
|---|---|---|---|
| 证据记录 | 采集器文章、通报、报告 | 某个来源在某个时间说了什么 | 不可以；默认“待核验” |
| 结构化观测 | finance/TACO/geo-v6/Treasury | 有单位、频率、历史序列的数值 | 只能说明数值变化，不能自动证明原因 |
| 主题/维度候选 | 关键词、采集器绑定、扩展显式字段 | 把材料放入美伊、俄乌及其子维度 | 是检索入口，不是事实判定 |
| 资产分析 | 指标 + 候选证据 + 规则版本 | 说明可能的传导渠道、成立条件和反证 | 只能是条件性研究观点 |
| 情景 | 规则目录中的持续/升级/缓和路径 | 组织观察项和数据缺口 | 不计算概率 |
| 研究员复核 | `reviews` 表 | 对单条记录给出升级/持续/缓和/待研判判断 | 是人工研判，不改原始快照 |
| 问答/简报 | 当前快照上的检索、计算和可选模型增强 | 面向研究工作的解释和交付物 | 必须带引用并保留缺口 |

### 6.2 研究员实际使用流程

1. **选边界**：选择快照、主题（美伊/俄乌/综合）、维度和报道日期范围。所有结果都绑定快照，避免同一页面混用不同采集时点。
2. **看覆盖**：先看数据源面板的项目数量、来源状态、失败来源、缺失发布时间/采集时间和归档文件；这一步判断“有没有数据”，不判断“结论是否成立”。
3. **看线索**：风险监测地图按事件类别、态势信号和报道关联地点聚合；数字是报道数，点位不是实时部署，不能把热闹程度当冲突强度。
4. **回到证据**：证据台账按中文/原文/来源检索并分页；打开详情查看原文、采集时间、分类依据、链接健康、上游抽取和关联地区。对关键记录提交研究员复核。
5. **看量化变化**：量化指标页展示当前值、前值、变化额/变化率、频率、口径、数据时效和来源；滞后或质量异常的观测保留查阅，但不进入当前条件判断。
6. **做业务研判**：资产关联页把市场观测和主题证据分开，给出传导渠道、成立条件、反证、下一观察项和待补数据；情景页用同样方式比较三条路径，不给出发生概率。
7. **向研究助手追问**：问答先做本地关键词检索和程序计算，再按问题需要追加资产/情景规则；答案展示 facts、引用、推论、缺口和处理步骤，点击引用可以回到证据详情。
8. **形成交付物**：研究简报以完整快照为边界，综合两个主题的近七日材料、指标变化、资产矩阵、情景和缺口，可保存、下载和与历史版本 diff。

### 6.3 八个 UI 入口分别解决什么问题

| UI 入口 | 实际消费 | 适合回答的业务问题 |
|---|---|---|
| 风险监测 | workspace 的地图轻量记录 | 哪些主题/事件类别有报道线索、关联地区在哪里 |
| 证据台账 | `/api/evidence` 分页摘要 + 详情接口 | 原始来源是什么、发布时间/采集时间/链接状态如何 |
| 情景推演 | `analysis().scenarios` | 如果持续/升级/缓和，分别需要什么条件、什么会推翻判断 |
| 数据源 | topics、projects、sources、archive | 哪个采集项目接入了、哪个来源失败、缺什么字段 |
| 智能问答 | `/api/ask` | 某个问题在当前快照和筛选范围内有哪些事实、指标和缺口 |
| 量化指标 | `snapshot.observations` 的指标视图 | 当前值与前值怎么变、是否新鲜、口径和来源是什么 |
| 资产关联 | `analysis().assets` + `important_metrics` | 证据和市场观测如何形成条件性资产传导路径 |
| 研究简报 | `/api/briefs` | 把当前快照整理成可引用、可下载、可比较的研究交付物 |

### 6.4 当前 UI 的真实业务边界

- 地图、证据列表和详情是同一快照的三种传输投影，不是三份独立数据。
- `situation_signal`、`event_category`、主题和维度都是检索与组织字段；只有研究员复核才会覆盖 UI 中的态势分类，且保留 `automatic_signal`。
- 资产卡片的“偏正面/偏负面/债价承压”等标签描述规则条件，不是价格预测、投资建议或冲突因果证明。
- 问答中的“程序计算”是由指标历史和规则生成的事实片段；“模型推论”即便经过证据 ID 校验，也仍标记为待研究员核验。
- 简报里的“近七日”是 takeaway 的取材窗口，不代表全量数据只有七天；完整快照仍保留历史记录和指标序列。
- UI 的“更新快照”只导入当前目录；如果要获取新数据，业务操作必须先运行采集器，再回到 UI 导入。
