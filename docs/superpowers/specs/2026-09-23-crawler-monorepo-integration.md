# 爬虫单体仓库整合设计

日期：2026-09-23

## 目标

将两个 WorkBuddy 目录中的 19 个采集器整合进地缘政治智能体，使应用、采集器、研究材料和运行脚本形成一个可迁移、可验证、适合后续上传 GitHub 的项目。原 WorkBuddy 目录保持只读。

## 仓库结构

```text
项目源码/
├─ collectors/               # 采集器源码、配置和项目说明
│  ├─ collectors.json        # 统一注册表
│  └─ <collector>/
├─ backend/                  # FastAPI 与数据适配
├─ src/                      # React 前端
├─ knowledge/                # 研究材料
├─ data/                     # 本地数据库、模型和运行数据（Git 忽略）
│  └─ collector-output/      # 迁移的历史采集结果
├─ examples/demo-data/       # 小型、可追溯的演示快照
└─ scripts/                  # 统一采集、导入及仓库检查
```

## 迁移边界

进入版本控制：

- 采集器主程序、共享模块、验证程序、必要配置及 README。
- 华泰中东简报、deep-research-report 与现有核对报告，放入 `knowledge/`。
- 统一采集注册表、便携运行脚本、数据适配代码和测试。
- 小型演示快照；其中只保留应用启动和界面展示需要的数据。

仅在本地保留并由 Git 忽略：

- `output/` 下的累计记录、原始网页、CSV、JSONL、Excel 和历史归档。
- SQLite 数据库、本地翻译模型、日志、缓存、构建产物和依赖目录。
- `.env`、密钥、令牌、本机代理和计划任务状态。

不迁移：

- `.workbuddy/`、`__pycache__/`、测试探针、临时负向测试输出、旧备份脚本和编译缓存。

## 数据运行方式

采集器源码位于 `collectors/<name>`，运行结果统一写入 `data/collector-output/<name>`。为兼容尚未支持外部输出目录的旧采集器，统一运行器在执行时为其建立运行目录或把产物同步至统一数据目录；应用只读取统一数据根目录。

`collectors/collectors.json` 记录采集器名称、主题、入口脚本、自检方式、输出类型及启用状态。统一脚本支持运行全部采集器、单个采集器、按主题运行和仅验证输出。

应用不再默认依赖用户目录下的 WorkBuddy 路径。默认数据根目录从仓库位置计算，同时保留 `CRAWLER_ROOT` 环境变量供高级部署覆盖。

## TACO 接入

`taco-monitor` 作为市场压力与资产验证采集器接入。其五因子 TACO 指数、五项输入和霍尔木兹观察指标必须保留角色区分：观察指标不被描述为指数成分。适配层读取结构化结果并生成量化指标；任何缺失、前值填充和源滞后继续显示在口径说明中。

## GitHub 可发布性

仓库检查脚本验证：

- 没有 `.env`、密钥、令牌或个人绝对路径进入待提交文件。
- 没有超过阈值的大文件、数据库、模型或完整采集历史进入版本控制。
- 每个启用采集器都有入口、配置和说明。
- 演示快照能够在无 WorkBuddy 目录时被导入。

许可证由仓库所有者在公开发布前选择，本次不替用户指定开源许可证。

## 验收标准

1. 19 个采集器均出现在统一注册表，源码可从当前项目定位。
2. 原 WorkBuddy 目录无需存在，项目仍能启动并载入本地迁移数据或演示快照。
3. 统一采集脚本可列出、选择、运行和验证采集器，失败相互隔离并生成汇总报告。
4. TACO 数据进入量化指标体系，口径与来源可追溯。
5. 后端测试、前端构建和完整启动检查通过。
6. 仓库检查不发现密钥、个人绝对路径或不应提交的大文件。
