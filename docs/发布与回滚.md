# GeoAgent 构建、正式发布与回滚

适用配置：[GitLab CI](../.gitlab-ci.yml)、[发布脚本](../scripts/ci/sealos-release.sh)。
正式站点：<https://geoagent.lhotsetech.com/>；GitLab 项目：<https://gitlab.lz.internal/yujunjun/GeoAgent>。

## 触发规则

| 操作 | 自动执行 | 是否更新正式环境 |
| --- | --- | --- |
| push 普通分支、main | Docker 构建、TypeScript/Vite 构建、完整后端 pytest、JUnit 报告 | 否 |
| 提交/更新 MR | 同上；避免同一分支 push 与 MR 重复运行 | 否 |
| push `geoagent-test-v1.0.0` | 同上，额外保存镜像 tar、校验和、镜像 ID | 否，没有测试站点 |
| push `geoagent-prod-v1.0.4` | 同上，验证 tag 受保护且提交已合入 main | 验证通过后，手动运行 `geoagent:sealos:deploy` 才发布 |
| 在正式 tag 流水线运行 `geoagent:sealos:rollback` | 校验发布归属、恢复该次发布前的镜像、健康检查 | 是，手动操作 |
| 其他 tag（例如 `v1.0.0`、PiChat 的 `stocklink-prod-*`） | 不创建流水线 | 否 |

版本号必须是三段数字，不支持 `-rc1` 等后缀。示例版本号仅为示例，使用前检查已有 tag。
仅提交或合并 main **不会发布正式环境**。与初版“正式 tag 自动部署”相比，现在增加了手动发布关口。

## 日常提交与测试构建

在自己的开发分支提交需要的文件，push 并创建 MR。不要把 `.env`、kubeconfig、私钥、本机数据库加入 Git。

```powershell
git switch -c feature/my-change
git add <本次修改的文件>
git commit -m "描述本次修改"
git push -u origin feature/my-change
```

MR 检查通过并完成审核后合入 main。如需留存一个测试构建：

```powershell
git fetch origin main --tags
git tag -a geoagent-test-v1.0.0 origin/main -m "测试构建 1.0.0"
git push origin geoagent-test-v1.0.0
```

`verify` 在新容器的 `/tmp` 中生成演示快照，执行完整 `tests/`，不连接生产 SQLite。
TypeScript 检查和 Vite 构建由 Dockerfile 的 `npm run build` 执行。
测试 tag 与生产 tag 各自构建；同一次生产流水线的部署使用自身验证过的镜像，不再次构建。
这不是把测试 tag 的镜像直接提升为生产镜像。

## 正式发布

1. 将代码合入 main，确认 MR/分支检查通过。确认没有正在执行的采集任务，发布期间不要启动新采集。
2. 创建一个从未使用过的正式 tag。`geoagent-prod-*` 已设为受保护 tag，仅 Maintainer 可以创建。

```powershell
git fetch origin main --tags
git log -1 --oneline origin/main
git tag -a geoagent-prod-v1.0.4 origin/main -m "正式发布 1.0.4"
git push origin geoagent-prod-v1.0.4
```

3. 打开 GitLab → 构建 → 流水线，进入该 tag。等待 `geoagent:sealos:verify` 通过。
4. 检查目标版本后，点击 `geoagent:sealos:deploy` 的运行按钮。只点 deploy，不点 rollback。
5. 等待 deploy 通过，并登录正式站点检查关键页面。流水线不会自动验证真实 PiChat 对话或所有采集源。

发布执行：校验主分支/受保护 tag → ACR 登录与集群检查 → 制品 SHA-256/镜像 ID 校验 →
加载已验证镜像并推送 ACR → SQLite 一致性备份 → 保存发布记录 → 原子校验 Deployment 版本并更新应用镜像 → 健康检查。

目标固定为 Sealos 广州 `ns-d40dap45` 中的 `deployment/geoagent`，只更新 `geoagent` 容器镜像。
网关、代理 sidecar、Secret、环境变量和 PVC 保留。数据库仍为 SQLite。
单副本 `Recreate` 更新会有短暂中断。脚本发现采集锁时拒绝发布，包括需要人工核查的残留锁；不会自动删锁。
采集检查是发布前检查，不是全站维护锁，运维仍需避免发布期间发起新任务。

## 发布验证与记录

- rollout 等待上限 300 秒；内部 `/api/status` 必须返回 200 且包含 snapshots。
- 从 Runner 访问公网 HTTPS `/api/status` 必须返回 401，确认 TLS/入口/鉴权仍生效；这是匿名检查。
- 验证作业的 JUnit 与 tag 镜像制品保存 7 天，部署/回滚报告保存 90 天。需要延迟发布时在 GitLab 保留制品，或发新 tag 重新验证。
- 部署/回滚报告：作业产物 `release/geoagent-release.txt`，记录提交、tag、流水线和前后镜像及最终状态。
- 集群发布记录：ConfigMap `geoagent-release-<流水线ID>`，记录前后镜像、提交及备份路径；不存凭据。
- 数据库备份：PVC `/app/data/release-backups/<流水线ID>/`。使用 SQLite backup API，并做 integrity_check。
  包含 `research.sqlite3` 和存在时的 `collection-runs/ledger.sqlite3`。数据库文件不上传到 GitLab。
- 备份保留在同一个 PVC，**不是异地灾备**，没有自动清理。需关注磁盘余量并另行制定保留策略。

## 手动回滚

1. 找到要撤销的那一次正式发布流水线。先核对其 deploy 报告与当前线上版本。
2. 点击该流水线的 `geoagent:sealos:rollback`。它不依赖 deploy 成功，因此发布后的健康检查失败时也可运行。
3. 脚本读取该次发布前的镜像，并检查当前线上镜像及发布归属仍匹配该流水线；如果已有新发布或外部修改，拒绝覆盖。
4. 回滚完成后，再次执行 rollout、内部 API 和公网匿名鉴权检查。查看 **rollback 作业本身** 的状态和报告。

回滚作业为可选手动作业（`allow_failure: true`），其失败不会使之前成功的流水线变红，不能仅看流水线总状态判断回滚成功。
回滚与部署使用同一个 `resource_group`，互斥执行。发布序号不会随回滚降低，旧 deploy 按钮也不能覆盖新版本。
回滚按钮只撤销对应流水线，不支持任意历史版本选择；初版流水线没有发布记录，不能用新按钮回滚它们。

**回滚只恢复程序镜像，不自动恢复 SQLite、Secret 或配置。** 不兼容数据库结构变更需单独评估旧程序兼容性。
没有失败自动回滚：失败保持可观察状态，由运维决定回滚或修复后发布。
如果必须恢复数据库，应进入维护窗口、停止写入、保留现有数据副本、检查备份，再由运维显式恢复；不要在线覆盖 SQLite 文件。

## 故障处理

| 情况 | 处理 |
| --- | --- |
| 没有流水线 | 检查 tag 格式、tag 保护和是否只推送了分支 |
| verify 失败 | 修复构建/测试；不要跳过门禁。测试没有生产凭据 |
| 制品过期或校验失败 | 使用新 tag 重新构建验证，不手改 tar 或校验文件 |
| 采集锁存在 | 等待采集完成；残留锁先确认无活动任务，再按采集运维流程恢复 |
| ACR/工具镜像拉取失败 | 检查 ACR 凭据/网络；部署工具已镜像到 ACR，不在线下载 kubectl |
| 记录已存在或流水线过旧 | 不覆盖原记录；若已更新镜像，使用该流水线 rollback；未更新则检查原因后用新 tag |
| rollout/健康检查失败 | 查看 Pod/容器日志和 deploy 报告；符合归属条件时手动 rollback |
| rollback 拒绝 | 可能已有更新版本或外部配置变更；核查实际线上状态，不删除保护标记绕过检查 |

同一次发布失败后，若已经生成数据库备份或发布记录，优先用新 tag 重做；不要删除历史 tag 再强推，也不要直接重试期待它重新覆盖生产。
Kubernetes 的 `rollout undo` 会恢复整个 Pod 模板，可能连带回退 sidecar/环境配置；本管线回滚只改应用镜像。

## GitLab 配置与维护

Runner 标签：`data-ingestion-platform`、`artifact`、`shell`。现为共享 Linux shell Runner；只应运行可信项目代码，不能视为不可信代码的安全沙箱。

以下变量均为 protected，环境 scope 精确为 `geoagent-sealos-production`：

| 变量 | 类型/用途 |
| --- | --- |
| `GEOAGENT_PROD_KUBECONFIG` | File；Sealos kubeconfig，masked/hidden |
| `GEOAGENT_PROD_ACR_USER` | ACR 用户名 |
| `GEOAGENT_PROD_ACR_PASSWORD` | masked/hidden；ACR 密码 |

验证作业不声明生产 environment，因此不注入这些环境级凭据。部署/回滚临时 Docker 登录目录在作业退出时清理。
生产 tag 保护为 `geoagent-prod-*`；不要移除保护，也不要开启 CI debug trace。
需要更新部署工具时参见 [工具镜像说明](../deploy/ci-tools/README.md)。

## 与 PiChat 的关系

参考 PiChat 的候选制品、生产手动发布、健康检查、独立手动回滚和报告留存方式。
GeoAgent 使用 Sealos 镜像与 PVC，未复制 PiChat 的 SSH 发布路径、数据库重建、沙箱或产品发布脚本。
按本次确认，**没有测试环境部署站点**；测试构建与自动化验证已纳入流水线。自动数据库迁移/恢复、异地备份、浏览器 E2E、零停机发布仍不在本管线范围内。
