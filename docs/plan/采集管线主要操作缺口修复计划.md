# 采集管线主要操作缺口修复计划

版本：v0.3（手动执行排除项已修复，运行页职责已收窄）
日期：2026-10-02  
关联方案：[采集管线常驻化与监控重构方案](./采集管线常驻化与监控重构方案.md)

## 1. 目的和结论

本计划用于修复三视图原型与真实业务操作之间的断点：让运行批次、来源核对、候选加工、发布门禁、统一导入、快照和工作快照形成可追踪的闭环，并保证问答/简报只能使用已经确认的工作快照。

本计划是持续修复计划。2026-10-02 已完成 P0 的第一轮实施，仍有实时进度、快照反查和来源覆盖等 P1/P2 工作未完成。

## 1.1 本轮实施记录（2026-10-02）

- GAP-01：已实现 `collector_reviews` SQLite 持久化、来源/候选/门禁/导入/快照核对状态，以及候选加工审计、统一导入明细真实接口；页面刷新后可重新读取核对状态。
- GAP-02：采集服务会把每个采集器本轮的来源状态文件归档到 `data/collection-runs/<run_id>/<collector_id>/source-status/`；历史来源查询不再回退到当前发布目录。尚未完成输出 manifest hash 和快照反查。
- GAP-03：问答、简报后端统一要求 `working_snapshot_id`，前端浏览快照与工作快照分离；查看数据范围不会隐式改变分析依据。
- GAP-06：已增加仅重试导入入口；部分成功批次必须先记录门禁批准，再显式允许部分成功导入，不重新执行采集器。
- UI 操作补充：运行流程中有后续动作的阶段卡片本身可点击，并支持键盘 Enter/空格触发；内部按钮不会重复触发卡片动作。运行页已收窄为“运行批次 / 来源抓取 / 采集输出”三段，只负责抓取进度、异常来源和输出门禁；统一导入、快照、工作快照和问答/简报不再堆在当前运行卡片中。
- 配置执行修复：手动“立即执行”和失败重试现在读取同一份项目调度配置的 `exclude_ids`；显式执行被排除的采集器会返回 409，批量执行会跳过排除项并在运行报告中保留排除说明。此前 `collector_jobs.submit()` 未接收排除项，导致手动全量执行绕过调度配置，这是 `taco-monitor` 被执行的直接原因。
- 测试证据：`.venv/bin/python -m pytest -q` 为 `139 passed`；`npm run build` 通过。新增了显式执行排除采集器的回归测试。
- 本轮未宣称外网采集全部成功；真实失败仍以运行报告和来源产物为准。

- 当前最近可读运行批次为 `manual-20261002T120354Z-f249f96d`，该批次只执行了 `taco-monitor`，并因 `CO1` 无出口代理失败；它的 `excluded_collector_ids` 为空，说明是在本次修复前入队的旧任务。更早的 `manual-20261002T103546Z-e1b556b5` 则是 19 个采集器中 18 个完成、1 个失败。
- 两个批次都处于未通过采集输出门禁的状态，导入状态为 `skipped_collection_status`，没有生成新的 `snapshot_id`。
- `/api/collector/sources?run_id=...` 返回 14 个采集器的来源产物、442 个来源；这不等于 19 个采集器都具备本批次来源状态。
- 当前快照库有 5 个不可变快照，但 `/api/workspace-selection` 返回未选择工作快照。
- 当前测试和构建证据为 `.venv/bin/python -m pytest -q`：139 passed、1 个弃用警告；`npm run build` 通过。内嵌浏览器的页面结构已通过 Vite 构建验证，仍需在浏览器中做最终视觉验收。

## 4. 目标操作闭环

```text
当前运行（抓取进度）
  ↓ 查看批次范围、排除项、执行中/成功/失败来源和输出门禁
采集池与来源（已抓取数据）
  ↓ 查看记录列表、来源详情、过滤条件和统计；按当前条件生成快照
快照版本谱系
  ↓ 浏览不可变版本、查看详情；调整条件必须生成新的派生版本
工作快照
  ↓ 明确确认并持久化
问答 / 简报
  ↓ 只读取已确认的工作快照
```

每一个箭头都必须有“可查看的数据、可执行的动作、可追踪的结果”。只有文字提示或前端 checkbox 不算完成。

## 5. 分阶段实施计划

### Phase 0：冻结数据和状态契约

目标：先消除“当前运行、当前发布目录、历史运行、工作快照”混用。

- 为 `collector_runs` 增加明确的 `run_id`、`source_artifact_root`、`output_manifest_hash`、`review_status`、`gate_decision` 字段或等价结构。
- 每个采集器的来源状态、stdout/stderr、输出 manifest 写入 `data/collection-runs/<run_id>/<collector_id>/`。
- 快照保存 `created_by_run_id`、输入 manifest、门禁结果和导入策略。
- 明确 `display_snapshot_id` 与 `working_snapshot_id` 的前端语义；查看数据范围不能隐式切换工作快照。

验收：历史批次读取不会引用当前发布目录；快照可以反查输入 run。

### Phase 1：完成 P0 人工核对和门禁

建议接口（名称可调整，但必须有同等能力）：

```text
GET  /api/collector/runs/{run_id}/review
PUT  /api/collector/runs/{run_id}/review/{item_id}
POST /api/collector/runs/{run_id}/gate
GET  /api/collector/runs/{run_id}/candidate-audit
GET  /api/collector/runs/{run_id}/import-detail
POST /api/collector/runs/{run_id}/import-retry
```

UI 改动：

- “来源抓取”按钮必须定位到本批次真实异常来源；找不到来源产物时显示“本批次未提供来源状态”，不能跳到其他采集器。
- “候选加工”和“统一导入明细”改成真实入口；如果数据没有记录，显示未记录原因和下一步动作。
- 人工核对清单改为受控状态，并显示保存结果、操作者和时间。
- 发布门禁显示自动判定、阻断原因和“批准部分成功/拒绝”操作。

验收：对当前 `taco-monitor` 失败批次，可以从运行视图定位失败原因、记录人工决策，并在不重新抓取的情况下选择是否导入。

### Phase 2：修复工作快照和下游分析边界

- 问答、简报、指标和研究视图统一从后端读取工作快照上下文。
- “查看数据范围”只打开只读研究视图；“设为工作快照”才改变工作上下文。
- 未确认工作快照时，UI 和后端都拒绝生成问答/简报，返回明确错误码。
- 顶部“数据快照”选择器区分“浏览版本”和“工作版本”，避免用户误认为两者相同。

验收：页面刷新、切换 tab、重新启动服务后，工作快照仍一致；浏览其他版本不会改变问答依据。

### Phase 3：实时运行和历史可观测性

- 当前运行视图轮询或订阅账本事件，而不是只等待 `results.json`。
- 展示队列、执行中、重试、完成、失败、导入、快照和人工等待等事件。
- 来源状态按 run 读取，当前运行和历史运行使用不同的产物路径。
- 增加取消运行和异常中断的用户操作及事件。

验收：运行中刷新页面可以恢复当前批次；历史运行不会被当前发布目录覆盖；服务重启后的运行明确为 `abandoned`。

### Phase 4：采集池和快照视图完善

- 采集器分组从注册表真实投影，不再统一为“未分类”。
- 来源总览拆分正常、失败、空响应、过期、停用、未知和缺失产物。
- 来源列表支持状态过滤、搜索、分页和查看完整错误。
- 历史运行支持时间范围、采集器过滤、分页和运行状态筛选。
- 快照谱系展示运行来源、输入 manifest、门禁结果、导入统计和复用原因。

## 6. 测试和验收矩阵

### 后端

- 同一 `run_id` 的来源状态不会读取另一个 run 的发布文件。
- 部分成功的门禁批准、拒绝、重复提交和服务重启恢复均有测试。
- 导入重试不会重新执行采集器，并且不会覆盖上一份完整快照。
- 非工作快照不能生成问答和简报。
- 快照能够反查 run、manifest 和来源覆盖。

### 前端

- 当前运行：从来源阶段进入正确采集器，候选加工和导入明细有真实入口。
- 人工核对：勾选、保存、刷新、返回后状态一致。
- 门禁：批准/拒绝后阶段状态、导入状态和快照状态一致。
- 快照：浏览版本不改变工作版本；确认后问答/简报使用新工作版本。
- 运行中：刷新页面仍能恢复当前运行和事件尾部。

### 真实运行验收

- 至少验证一次完整成功运行、一次部分成功运行、一次导入失败、一次取消/中断恢复。
- `taco-monitor` 的 CO1 无出口代理场景必须明确显示为来源/采集器失败，不得伪装为快照成功。
- 每次验收记录 `run_id`、`snapshot_id`、`import_status`、失败来源、门禁决策和日志位置。

## 7. 暂不处理的事项

- 不在本计划内把所有来源改为 Browser Agent；先完成 run 级产物、门禁、重试和可观测性。
- 不把当前 135 个本地测试通过解释为真实外网采集全部成功。
- 不删除现有历史报告和快照；迁移必须保留旧报告的不可用/缺失字段语义。

## 8. 完成定义

本计划完成的标准不是“三个 tab 能打开”，而是：

1. 操作者能从一个失败阶段进入正确的 run 级证据；
2. 每个需要人工确认的步骤都有真实数据、真实动作和持久化结果；
3. 运行、发布目录、导入、快照和工作快照之间可以双向追溯；
4. 未确认工作快照不能进入问答和简报；
5. 运行中、失败、部分成功、导入失败和中断恢复在 UI 上有不同且可解释的状态。
